## 3. 画面構成 / 画面遷移

### 3.1 画面の種類

```
GameProvider
 └─ Screens (screen: 'field' | 'battle' | 'town' で出し分け)
     ├─ FieldScreen(横スクロールフィールド)
     ├─ BattleScreen(戦闘 / 現状プレースホルダー)
     └─ TownScreen(町 / 未実装、仕様は今後詰める)
```

画面遷移は `GameContext` が一元管理する。
- `goToBattle(enemyId)`: フィールド上で敵と接触した際に呼ばれ、`screen` を `'battle'` に切り替える
- `goToField()`: 戦闘終了後にフィールドへ戻る
- ゴール到達時の遷移(関数名・実装未定): フィールドのゴールに到達した際に呼ばれ、遷移先(次のフィールド or 町)を3.2節の「世界マップ」定義に従って決定する

### 3.2 世界マップ(ステージ間遷移の定義)

#### 決定事項(2026-07-11 時点)

- 世界マップ全体としては**分岐を許容する**。ただし分岐が発生するのは**町画面のみ**であり、フィールド画面自体は常に一本道(単純な左右移動)。フィールドごとに個別ハードコードするのではなく、**「世界マップ」という独立したデータ**としてステージ間の接続を定義する(`levelData.ts` と同様にデータ駆動)
- **ゴール判定**: フィールド画面の左端 or 右端(画面/ワールド端の線)に到達したことをもって次画面への遷移とする。敵接触のような矩形オーバーラップ判定ではなく、端の通過判定
- **町画面の構造**: フィールド画面と同様、一本のライン上を左右移動する構造。町の中には以下のような要素/施設が配置される
  - 宿屋、ショップ、協会、その他イベント、話しかけ可能な住人
  - フィールド画面へつながる道(左右、町によってはさらに奥へ)
- **町とフィールドの接続関係**:
  - 町の左端(元来た道)を抜けるとフィールド画面へ遷移し、そのフィールドでは**左へ進む形**で入る
  - 町の右端(先へ進む道)を抜けると別のフィールド画面へ遷移する(**右へ進む形**で入る)
  - 町によっては「奥」へ進む道があり、その場合は町の中でL字に折れる形になるが、接続先のフィールド画面側は通常通り右か左のどちらかへ進む形になる(フィールド側は常に一本道という原則は変わらない)
  - つまり移動できるフィールドは、常にその町に隣接する(接続されている)フィールドに限られる
- **現在地の永続化**: 世界マップ上のどのノード(フィールド/町のどこ)にいるかは、アプリ終了後も保存し復元する
- **世界マップの開示(決定)**: 世界マップ画面(俯瞰表示など)は、プレイヤーが訪れたことのあるノードのみを開示する(フォグ・オブ・ウォー的な仕様)。訪問済みノードの記録(`visitedNodes`)は7.2節の`PlayerState`に持たせ、図鑑と同様にゲームオーバー時も維持する
- **町画面での遷移方式(決定、2026-07-19時点)**: フィールド画面と異なり、町画面では**ワールド端への到達では遷移させない**。町の中の任意の位置に「門」を配置し、**門に近づいてインタラクトボタン(○)を押す**ことで遷移する。門は町のどの位置にも置けるため(端だけでなく町の途中でもよい)、1つの町に3つ以上の門を持たせることもできる(3.3節の町1が実例)。フィールド画面の「端への到達で遷移」という方式(4.1節)はそのまま維持し、変更しない。
  - 門は他の施設(宿屋・ショップ等)と同じ`facilities`配列内に`kind: 'gate'`として配置し、`exit`(接続に使う出口名)を持つ
  - 門に`requiredItem`が指定されている場合はアイテムゲート(3.2節`requiredItem`)。**インベントリ未実装の現状では、指定があれば常に通行不可として扱い**、「何かが足りないようだ」等のメッセージを表示する(7.2節のアイテム所持判定が実装され次第、実際のチェックに置き換える)
  - スポーン位置: 町に入るときは、入ってきた出口(`entrySide`)に対応する門の脇にスポーンする。該当する門が無い場合(ゲーム開始時点の町0など)は町の中央にスポーンする
- **データ構造**: ノード(フィールド/町)に出口情報を埋め込むのではなく、**接続(道)を1本のフラットな配列として列挙する**方式を採用する。理由は、繋ぎ替え・追加・削除のたびに編集する箇所を1エントリだけに抑え、後から調整しやすくするため。

  ```ts
  type NodeId = string; // 'field_01', 'town_forest' など
  type ExitSide = 'left' | 'right' | string; // 町の奥ルートなどは 'depth' 等の任意の名前を使う

  type WorldMapConnection = {
    from: { node: NodeId; exit: ExitSide };
    to: { node: NodeId; exit: ExitSide };
    oneWay?: boolean; // 通常は不要(双方向がデフォルト)
    requiredItem?: ItemId; // このアイテムを永続アイテムとして所持していないと通行不可(7.2節 `keyItems` を参照)
  };

  const WORLD_MAP: WorldMapConnection[] = [
    { from: { node: 'field_01', exit: 'right' }, to: { node: 'town_forest', exit: 'left' } },
    { from: { node: 'town_forest', exit: 'right' }, to: { node: 'field_02', exit: 'left' } },
    { from: { node: 'town_forest', exit: 'depth' }, to: { node: 'field_03', exit: 'left' } }, // 奥ルート
    { from: { node: 'town_forest', exit: 'right2' }, to: { node: 'field_04', exit: 'left' }, requiredItem: 'feather' }, // アイテムゲート例
  ];
  ```

  - 起動時にこの配列から `(node, exit) → 接続先` のルックアップテーブルを1回だけ構築し、ゲーム中はそれを参照する
  - `exit` の名前数に制限はないため、町ごとに `left` / `right` に加えて `depth` のような奥ルート用の出口を任意の数だけ追加できる
  - ステージの中身(足場・敵配置などの `levelData.ts` 相当)とは別ファイルに分離し、世界マップの接続情報だけをこのファイルに集約する
  - **アイテムゲート判定**: `requiredItem` が指定された接続は、プレイヤーの `PlayerState.keyItems`(7.2節)に該当IDが含まれているかで通行可否を判定する

## 4. フィールド画面 仕様

### 4.1 実装済み(現状のコード基準)

- 毎フレーム更新(`requestAnimationFrame`)による物理演算ループ
- 左右移動: 画面下部のボタン(◀▶)を押している間、一定速度(`MOVE_SPEED`)で移動
- ジャンプ: ▲ボタン押下で `JUMP_SPEED` の初速、重力(`GRAVITY`)で落下
- 足場との当たり判定: `PLATFORMS`(手作りデータ)に対する着地判定。落下中のみ判定し、すり抜けを防止
- カメラ: プレイヤー中心に追従し、ワールド端でクランプ(`WORLD_LENGTH` を超えない)
- 背景: 2レイヤーのパララックス(奥/手前で異なるスクロール速度)
- 敵: `ENEMIES`(手作りデータ)に基づき中心位置から左右に往復パトロール
- エンカウント: プレイヤーと敵の矩形が重なったら `goToBattle(enemyId)` を呼び出し、戦闘画面へ遷移

### 4.2 データ駆動の設計

- ステージのレイアウト(足場・敵配置)は `src/data/levelData.ts` に集約
- 調整用パラメータ(重力・速度・サイズ)は `src/data/constants.ts` に集約
- → 今後ステージを追加する場合は `levelData.ts` 相当のファイルをステージごとに用意する想定(詳細は未決、6章参照)

- 現状はプレイヤー・敵・足場すべて色付き矩形の仮グラフィック

## 5. 戦闘システム 仕様

### 5.1 基本方式(決定事項)

- **コマンド選択式バトル**をベースとする(ドラクエ/FF系のメニュー選択)
- ただし選択できる行動(技)は複数種類あり、**行動の種類ごとに異なるアクション操作(タイミングタップ、スワイプなど)を伴う**
  - 例: 「たたかう」を選ぶとタイミングよくタップして威力が変動する
  - 例: 「とくぎA」を選ぶとスワイプ操作で軌跡を入力する
  - → スーパーマリオRPG/ペーパーマリオ系の「アクションコマンド」に近い設計
- アクションの成功度合い(Perfect / Good / Miss 等)によって、ダメージ量や効果が変動する想定

### 5.2 決定事項(2026-07-08 時点)

1. **行動カテゴリ**: 「たたかう / 必殺技 / アイテム / にげる」の定番4分類。「たたかう」「必殺技」はさらにサブメニューで具体的な技を選ぶ2段階構成。
2. **アクション種別のマッピング**: 汎用フレームワーク化する。技の種類は将来的に数十種を想定しており、個別実装ではなく「アクション種別(tap/swipe等) + 判定ルール」を共通の仕組みにして、技データ側でどの種別を使うか指定するだけで済む形にする。基本はタップとスワイプの組み合わせで構成する。
3. **ターン制御**: 完全ターン制(プレイヤー行動→敵行動の順)。ATB系のような戦闘中常時アニメーションループは採用しない。
4. **敵の攻撃へのガード**: 敵からの攻撃に対しても、プレイヤーはアクションコマンド(タイミングよくタップ等)でガード操作を行える。

### 5.4 パーティキャラ(仲間) 仮データ(ドラフト、2026-07-12時点)

#### 基本方針(決定事項)

- 仲間はひとまず**3体**を想定(今後増える可能性あり)
- ストーリーを進めてイベントが発生すると仲間になる(個々の発生条件は各キャラのイベント設計時に決定)
- パーティキャラは**経験値では成長しない**が、**ストーリーイベントを通じてステータス成長・技の追加はある**(5.3節6.を修正)。少なくとも HP・MP のパラメータを持つ

#### 仲間データ

**1. ウンチャン** — HP 20 / MP 15

- パッシブ: 敵から直接攻撃を受けると、攻撃してきた敵に状態異常「汚れ」(毎ターン1ダメージ)を付与する
- 技:
  - ウンチ玉: 単体2ダメージ、命中した敵に「汚れ」付与
  - スキャン: 敵の詳細情報を調べる(ダメージなし)
  - 乱れウンチ: MP消費2、ランダムに合計5ダメージ、命中した敵に「汚れ」付与
- フィールド上での役割: ゲームのヒントを提示する

**2. ピヨコ** — HP 20 / MP 20

- 技:
  - ピヨッチ: 最前列の単体に2ダメージ
  - ピヨダッシュ: MP消費2、敵全体に2ダメージ
  - ピヨキュア: MP消費4、主人公または特定の仲間のHPを10回復
- フィールド上での役割: 永続アイテム「羽」を使い、一定時間浮遊移動できるようにする(7.2節の時間制限つきアビリティを実際に発動するのはピヨコ、という位置づけ)

**3. バケモノ** — HP 20 / MP 20

- パッシブ: 直接攻撃を受けてもダメージ0(無効化)。かわりに自身のMPが2回復する(自己回復、確定)。ただし魔法攻撃を受けた場合はダメージ2倍
- 技:
  - レイホー: 単体2ダメージ、命中した敵に状態異常「震え」(1ターンの間、50%の確率で行動不能)を付与
  - カナシバリ: MP消費2、単体4ダメージ、命中した敵に状態異常「恐怖」(1ターンの間、確定で行動不能)を付与
  - 破滅の光: MP消費4、主人公のレベル−3以下の敵は即座に戦闘不能。それより高いレベルの敵に対しても確率で同様の効果
- フィールド上での役割: 一定時間、主人公を含むパーティ全体に透明状態を付与し、フィールド上の敵と接触しなくなる(ピヨコの羽と同様、時間制限つきのフィールドアクション)

#### 各技のアクションコマンド(決定事項)

- 各技はアクションコマンド(タップ/スワイプ等)の成功度合い(Perfect/Good/Miss)によって効果が変動する、という5.1節の共通ルールに従う
- 技ごとに具体的にどのアクション種別(タップ/スワイプ等)を割り当てるかは、5.2節2.の汎用フレームワークに従ってデータ実装時に個別に決定する(ドキュメント上のブロッカーではない)

#### この草案から見えてきた新しい仕組み

- **状態異常システム(新規決定)**: 「汚れ」「震え」「恐怖」のように、複数ターンにわたって効果を及ぼす状態異常の仕組みを導入する。一般化したデータ構造(継続ターン数、効果種別 [継続ダメージ / 行動不能確率 など])は未決
- **攻撃属性(物理/魔法)の弱点・耐性(新規決定)**: バケモノの「魔法攻撃で2倍ダメージ」のように、技に物理/魔法などの属性を持たせ、キャラごとに弱点・耐性倍率を持たせる仕組みを導入する。属性の種類・倍率のデータ構造は未決
- **即死/戦闘不能系の技(破滅の光が実例)**: レベル差に応じて即座に敵を戦闘不能にする技がある。7.1節の「行動(技)の定義テーブル」にこの手のロジックをどう組み込むかは未決

#### 未決事項/要確認

- バケモノの透明化(フィールドアクション)のチャージ/回復・発動条件(羽の`keyItemCharge`と同様の仕組みを使うか、パーティキャラ固有の別の仕組みにするか)

### 7.2 アイテム/インベントリ(決定事項ドラフト、2026-07-12 時点)

#### アイテム種別

| カテゴリ | 説明 | 所持の表現 |
|---|---|---|
| 消費アイテム | 使うと減る | 個数(`Record<ItemId, number>`) |
| 永続アイテム(キーアイテム) | シャベル・羽・シャチの笛など。世界マップのゲート判定(3.2節`requiredItem`)に使う | 所持有無の二値(`Set<ItemId>`) |
| 輝石(旧パワーストーン) | 技を増やす装備品(ペーパーマリオのバッジ相当)。**装備コスト制**で同時装備数に上限を設ける | 所持リスト + 装備リストを分けて保持 |
| お金 | 共通の所持金 | 数値 |
| 経験値 | **主人公のみ**が経験値で成長する(5.3節6.決定)。パーティキャラ(補佐)は経験値による成長はないが、ストーリーイベントによるステータス成長・技追加はある(5.4節参照) | 主人公の数値のみ |
| 図鑑 | モンスター/アイテム/輝石の3系統。「所持」とは別軸の「発見済みか」を記録 | それぞれ独立した`Set` |

- カテゴリは今後増える可能性があるため、`ItemDefinition` はカテゴリ別のunion型にしておき、追加時は union にメンバーを1つ足すだけで済む形にする
- 輝石の装備は**主人公のみ**が行う(パーティキャラは装備しない)

#### 型定義(ドラフト)

```ts
type ItemId = string;
type CharacterId = string; // パーティメンバー識別子

type ItemDefinition =
  | { id: ItemId; category: 'consumable'; name: string; description: string }
  | { id: ItemId; category: 'keyItem';    name: string; description: string }
  | { id: ItemId; category: 'kiseki';     name: string; description: string; cost: number };

// 主人公: 経験値で成長。レベルアップ時にHP/MP/KPのいずれかを選んで伸ばす
type ProtagonistState = {
  level: number;
  exp: number;
  allocated: { hp: number; mp: number; kp: number }; // これまでの成長選択の累計値。KPが輝石の装備コスト上限になる
};

type MoveId = string;
type StoryFlagId = string; // 発生済みのストーリーイベントを示すフラグ

// パーティキャラ(補佐): 経験値による成長なし。ただしストーリーイベントで成長・技追加がありうる
type PartyMemberState = {
  characterId: CharacterId;
  unlockedMoves: Set<MoveId>; // ストーリーイベントで解放された追加の技
  statGrowth: { hp: number; mp: number }; // ストーリーイベントで得た成長分(マスタデータの初期値に加算)
};

type PlayerState = {
  protagonist: ProtagonistState;
  partyMembers: PartyMemberState[]; // 現在加入している補佐キャラ
  consumables: Record<ItemId, number>;
  keyItems: Set<ItemId>;
  keyItemCharge: Partial<Record<ItemId, number>>; // 時間制限つきアビリティを持つ一部の永続アイテムのみ登録(例: 羽)
  kiseki: { owned: ItemId[]; equipped: ItemId[] }; // 主人公のみが装備する。装備コスト上限は protagonist.allocated.kp
  money: number;
  storyFlags: Set<StoryFlagId>; // 発生済みのストーリーイベント。パーティキャラの成長トリガー等に使用
  dex: {
    seenMonsters: Set<string>;
    seenItems: Set<ItemId>;
    seenKiseki: Set<ItemId>;
  };
  worldMap: {
    currentLocation: NodeId; // 現在地。ゲームオーバー時は 'town_0' に強制移動
    visitedNodes: Set<NodeId>; // 訪問済みノード(世界マップの開示に使用)
  };
};
```

#### 主人公の成長方式(決定事項)

- 主人公のみが経験値で成長する。パーティキャラ(補佐)は経験値による成長がなく、戦闘には主人公の補佐として参加する固定パラメータのキャラクターという位置づけ
- **経験値の計算式(決定)**: 敵レベル > 自分レベルの場合、獲得経験値 = 敵レベル − 自分レベル(差が大きいほど多い)。敵レベル ≦ 自分レベルの場合は、1戦闘あたり固定で経験値1を獲得する(格下狩りでも経験値0にはならない)
- 一定の経験値を貯めるごとに1回成長でき、その際 **HP / MP / 輝石ポイント(KP)** のいずれかをプレイヤーが選んで伸ばす(選択制の割り振り)。KPは輝石の装備コスト上限そのものであり、輝石の装備上限は主人公の成長次第で変わる

#### 「時間制限つきアビリティ」を持つ永続アイテム(決定事項)

- 羽のように「フィールド上で短時間だけ使える」永続アイテムは、**一部の永続アイテムのみが持つ特殊ケース**として扱う(全永続アイテム共通の仕組みにはしない)。該当アイテムのみ `keyItemCharge` にチャージ値を持つ
- チャージの回復方法: **町で休む/時間経過による自然回復**に加えて、**魔力チャージアイテム(消費アイテム)による即時回復**の両方を用意する

#### ゲームオーバー時の初期化ルール(決定事項、2026-07-12時点)

`PlayerState` のうち、以下は**維持**する:
- `dex`(図鑑: モンスター/アイテム/輝石)
- `worldMap.visitedNodes`(世界マップの開示情報 = 訪れたことのある場所)

以下は**初期化**する:
- `protagonist`(レベル・経験値・HP/MP/KPの割り振り)
- `partyMembers`(仲間は全員離脱した状態に戻る)
- `consumables` / `keyItems` / `keyItemCharge` / `kiseki` / `money`(所持品・お金は全て失う)
- `worldMap.currentLocation`(**町0**へ強制移動。町0は世界マップ上、1-1のさらに左に位置する初期拠点。3.3節参照)

> **未決**: `storyFlags` をゲームオーバー時に維持するか初期化するかは未決定。維持する場合、`partyMembers` がリセットされた後に再加入した際、既に発生済みのイベントフラグをもとに成長分(`statGrowth`/`unlockedMoves`)をどう再付与するか(再加入時に自動で再計算するか等)も合わせて設計が必要

#### 収益化(マネタイズ)方針

- **決定**: アプリ内アイテムに課金要素(IAP)を入れる方針。3.2節の町間高速移動(馬車/ワープ)もこの一環として検討する
- 未決: 課金対象とする具体的なアイテム/カテゴリ、価格設計、ガチャ的な要素を含むか、ゲームバランスへの影響(課金アイテムで戦闘が有利になりすぎないか)

#### 未決事項

- パーティキャラのパラメータは少なくともHP/MPを持つことが決定(5.4節参照)。攻撃力・防御力等の追加パラメータの要否とマスタデータでの持ち方は引き続き未決
- ~~パーティキャラがフィールド上でアクションを行えるようにするか~~ → **決定**: 少なくともウンチャン(ヒント提示)・ピヨコ(羽での浮遊移動)は持つ(5.4節参照)。バケモノにフィールド上の役割を持たせるかは未確認
- 消費アイテムの「効果」の表現方法(例: 魔力チャージアイテムが特定の永続アイテムのチャージを回復する、という効果をどう定義するか)
- 図鑑の完成条件・報酬の有無
- ~~パーティメンバーの構成(何人まで、加入/離脱のタイミング)~~ → **決定**: ひとまず3体(今後増える可能性あり)。ストーリーイベントで加入(5.4節参照)。離脱の仕様は引き続き未決

## 8. パフォーマンス設計方針

**最優先事項は画面表示のカクつき解消**(2026-07-08 決定)。この方針は他の設計判断より優先する。

### 8.1 計測環境の構築

スマホ実機接続を保留した代わりに、WSL2上にAndroidエミュレータ(Pixel 6 / Android 14, AVD名 `nanashi_perf`)をKVMハードウェアアクセラレーション付きで構築した。GUI表示は不要なため `-no-window` のヘッドレス構成。`adb`経由でExpo Goをインストールし、`adb shell dumpsys gfxinfo <package> [reset]` でフレーム統計を取得する運用とした。

### 8.2 計測結果(ベースライン、2026-07-08)

`FieldScreen` で右移動ボタンを8秒間押しっぱなしにした状態で計測:

| 指標 | 値 |
|---|---|
| 総フレーム数 | 199 |
| Janky(遅延)フレーム | 162 (81.4%) |
| フレーム時間 50%tile | 69ms(60fps基準は16.6ms) |
| フレーム時間 99%tile | 150ms |
| Slow UI thread | 135/199 (68%) |
| Slow issue draw commands | 162/199 (81%) |

> 注: エミュレータはSwiftShaderによるソフトウェアレンダリングかつWSL2上の共有リソースのため、絶対的なfps値は実機より悪化する。ただし「GPU側ではなくUIスレッド側が支配的に遅い」という相対的な傾向は明確で、これは実機でも同じ構造的問題として現れると考えられる。

### 8.3 原因診断

`FieldScreen.tsx` が毎フレーム `setState`(`playerView` / `enemyViews`)を呼んでおり、`Player` / `Enemy` / `World` はいずれも `left` / `bottom` という**レイアウトに影響するスタイルプロパティ**で位置を表現している。これがフレームごとに React の再描画 → Yoga レイアウト再計算という重い処理を引き起こし、計測結果の "Slow UI thread" / "Slow issue draw commands" が支配的という傾向と一致する。

### 8.4 決定した対策

1. `Player` / `Enemy` / `World` / `Background` の位置指定を `left` / `bottom` から **`transform: [{translateX},{translateY}]`** に変更し、レイアウト再計算を避けてコンポジット処理のみで済ませる。
2. **`react-native-reanimated`** を導入し、`FieldScreen` の毎フレーム更新を JS側の `setState` ではなく shared value 経由(UIスレッド駆動)にする。JSスレッドの負荷やGCの影響を受けにくくなる。
3. この2点は戦闘画面のアクションコマンド(タップ/スワイプの精度)にも直結する共通基盤として、フィールド画面の改修と合わせて先に整備する。

改修後は同じ手順(右移動8秒間 + `dumpsys gfxinfo`)で再計測し、Before/Afterを比較する。
